## 根因和修复范围

冻结 `deployment-plans.json` 中的计划路径仍指向旧 AppData 地址。Codex 进程对该地址有应用目录重定向，而 Windows Task Scheduler 启动的原生进程没有同一视图。固定入口已经使用物理目录，但冻结配置内部的绝对引用仍不可达，所以预检能通过源码/依赖验证，真正驱动却在打开计划文件时失败。

只在已确认不存在的宿主路径建立目录和指向既有物理部署的 junction。没有替换已有目录，没有改写冻结计划、原包装器、安装源码、六个控制脚本或当前清单。原生探针在修复前后核验了两份计划的文件摘要；恢复调用再次验证原源码和环境，并实际读取了这些引用。

修复辅助任务首次返回 1，且自身结束回执未生成；未把这次辅助进程记为成功或补造回执。后续独立的原生只读探针证明 junction 已建立且指向正确目录，实际观察恢复进一步验证效果。辅助进程错误原因没有捕获，保持未确认；所有一次性诊断/修复任务均在结束后移除，持续任务仍只有原先两项。

## 结果与通知的限制

使用原冻结安装环境、原观察器和原输入执行两次独立离线重放，均 VERIFIED；回放进程禁止 Python 出站网络。原件摘要、输入时钟、记录 hash、固定策略与禁单权限通过检查。两个策略使用同一小时输入，不能当作两个独立市场事件；本轮也没有执行参考成交。

巡检保留该时点 2 份开始、2 份结束回执和 1 份有效结果，`original_gap_preserved=true`，不会把恢复抹平成最初成功。故障及恢复的原生通知均返回 DEFERRED_BY_USER_STATE，系统状态值为 2，尚无本轮 OS 显示确认。巡检因待发通知返回非零是保留的待处理状态，不等于没有发现故障；没有更改系统通知偏好来强行显示。

开发分支新增实际计划引用预检：逐一打开冻结部署中的两份绝对路径，要求解析后位于冻结计划目录、规范内容摘要等于已钉住的两个计划且不重复。窗口前观察入口仍不采集行情，但必须先完成这一预检与原源码/环境检查，失败写 FAILED_PREFLIGHT；成功跳过时附带 `prewindow_runtime_preflight`。窗口结束后的调用仍直接跳过。
