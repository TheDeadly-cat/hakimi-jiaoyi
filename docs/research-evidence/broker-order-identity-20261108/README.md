# 原订单确认与后续请求的编号接线

此前原下单确认已经进入账本，但运行中的 codec 没有采用该确认里的订单编号；后续查询和撤单测试依赖预置编号。本批让同一条原流程从没有订单编号开始，只有原确认成功保存并完整读回，才把精确的字符串编号绑定到已接受握手的同一 codec。后续查询、撤单和原费用请求构造均须使用这个编号及原权限合同；不会因此获得新的外部权限。

## 身份依据与新请求检查

`read_acknowledged_order(profile)` 从原 journal 完整重放结果中读取唯一的原 CLAIM、提交 ACTION、已保存 VERIFIED_RESPONSE 和已确认 outcome。它核对原账户、意图、证券/订单范围、双会话、观察包、原请求与响应哈希，以及 claim 中持有的编号，返回不可变的 `VerifiedAcknowledgedOrder`。它不增加事件、快照、期限或业务账本。

原响应未保存、保存结果不明、只有裸 OUTCOME、缺少字符串编号或存在矛盾确认时，不能采用编号。只读身份不把 ACK 解释为成交、费用终局或券商认证。编号保持不透明字符串，不转换为数值编号；锁定 SDK 对撤单请求中已弃用但必填的数值 `orderID` 使用 0，并把原编号放入 `orderIDEx`。当前官方[改单撤单](https://openapi.futunn.com/futu-api-doc/trade/modify-order.html)及[订单查询](https://openapi.futunn.com/futu-api-doc/trade/get-order-list.html)也把订单号定义为字符串；当前网页 v10.12 不替代锁定 10.7.6708/OpenD 的兼容验收。

v3 codec 的初始会话不能预置订单编号。采用过程要求实际接受的双握手与原提交会话一致；同源重复采用幂等，不同来源或编号冲突不覆盖现有绑定。新请求执行前，原协调器在停止屏障外重新读回身份；原 journal 在写事务内再次核对。实际写入屏障只校验已核对的不可变身份、当前会话、原操作范围、期限和停止状态，不在屏障内打开数据库或等待网络。

原提交的行情观察窗口到期，不会抹掉已保存的订单身份，也不会禁止仍在自己许可期限内的查询或撤单。已确认订单的后续管理只要求交易通道仍然活动，原行情通道失联不会阻止它；原双握手身份仍须一致，新提交仍要求两个通道活动。此批没有增加生产环境的 FIN 检测器，失联状态在专项中明确注入。它同样不会延长这些后续操作的 profile/permit、原 transport 或 keepalive 窗口，也没有隐式重连、重新下单或自动撤单。

## 历史记录与经济状态

v2 默认合同保留。已有 v3 事件格式没有变更，新完整确认要求只用于原写事务中的**新请求**；旧编号重放先返回原回执，历史 `_reduce` 合同不增加这项限制。旧版原件兼容样本由固定 `1f04c393` 的原 journal 生成，再由新实现读取，不能用新实现生成的记录冒充升级验证。

后续订单查询的累计成交字段作为原事实保存，不自动写成精确成交金额或经济观察。撤单 ACK 仍不是订单终局；费用未知、原预留、持仓归属和历史 UNKNOWN 均按原合同保留。只有既有的明确经济核对路径才能处理相应资金状态。

本批建立在 [PR #29](https://github.com/TheDeadly-cat/hakimi-jiaoyi/pull/29) 的提交前观察检查之上。公开的 [r7 研究与本地演练试用候选](https://github.com/TheDeadly-cat/hakimi-jiaoyi/releases/tag/v0.7.0.dev3-r7)保持原包身份，本批后续源码没有打入 r7。原生、独立 Windows 与三位新手实际验收仍待完成。

生产授权装配、价格来源及时效、行情/账户权利、真实资金/归属持仓、费用来源、OpenD 兼容与完整成交/经济核对链仍有独立工作。本批没有调用真实账户、运行 OpenD、启用 SDK context 或扩大权限。

- [完整 terminal 检查](full-terminal.json) **1016/1016 通过**，零失败、错误或跳过，452.602 秒。独立环境实际安装当前工作树，10 个改动输入前后字节一致；[环境核对](full-terminal-preflight.json)与[原日志](logs/full-terminal.log)保留。
- [实际 protobuf 最终检查](actual-protobuf-summary.json) **4/4 通过**，原 unittest 日志 428.903 秒，外层 452.526 秒。固定 12 类真实 protobuf、原 supervisor/worker、原 SQLite 和自持动态本机 TCP 共同运行；所有报文和现金均为明确的虚构测试值。
- [四个案例](actual-case-index.json)覆盖完整原确认→查询→撤单→再次查询及重开、共享停止、错误订单响应留存，以及已确认行情连接失联后的订单管理。正例按原 12 个操作 ID 读回，零新请求编码、编号采用、连接和发送；原数据库及请求注册文件字节不变。恢复时 codec 的订单编号始终为空，原记录先返回，不需重新取得派发资格。
- 失联案例明确关闭自持行情 socket、记录 fd 已关闭，并由 peer 观察 EOF；同时注入“已确认行情失联”的当前状态，再验证原交易连接上的查询和撤单。它不证明产品已能自动发现 FIN。交易通道失联时拒绝新请求的分支另由协调器专项验证。
- [旧 v3 原件](legacy-v3/original-action.json)与[来源](legacy-v3/origin.json)对应固定 `1f04c393` 原 journal：原 ACTION 为 14,996 字节，SHA256 为 `7106299471b3a9680a1d776dde1f58284149d182600919620aa495a66cb6972e`。新实现读取及同 ID 重放保持原回执、数据库和资金状态；新裸 ACK 请求仍被拒绝。

实际链只使用 2201 的订单累计字段，未增加 2211 逐笔成交查询，也未调用 2225 费用查询。部分成交、撤单确认和最后查询都没有自动形成经济 OBSERVATION、确切成交金额或费用终局。

新测试装配采用固定顺序：行情握手→四项行情查询→交易握手→提交及后续管理，避免在交易通道上等待无关的前置准备。原产品 RPC 15 秒、每通道 keepalive 30 秒和原查询观察窗口 30 秒均保持。实际探针的 worker wall 90 秒、READY 30 秒、消息 15 秒、退出 10 秒、peer 150 秒、外层 480 秒是独立测试预算；不作为生产启动或吞吐性能验收。

[历史验证](retained-attempts.json)单列旧源码范围：第一次完整检查 1014 项和旧实际三例都曾通过，随后审查发现后续管理多余地依赖行情通道活动，于是做了上述最小修正并增加断线案例。旧十个源码文件字节与回执均留存，不能将它们称为新源码验证，也不把单正例、定向检查或多轮结果相加。
