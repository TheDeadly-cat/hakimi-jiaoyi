# T5：独立回执巡检

新增`tools/observation_watch.py`，可以在观察启动器完全没有运行时，按预先声明的窗口识别缺少的启动记录；也能识别启动后超过335秒仍缺结束回执、明确失败、迟到及后续恢复。它只读取回执，不调用采集器或研究引擎，不推断进程一定退出，也不把巡检成功当成市场重放或调度已经激活。

## 核对方式

计划固定预期启动器、冻结包装器/原计划摘要及巡检、发送器、Windows助手的实际工具字节。正式窗口必须在创建计划时仍处于未来，并明确声明72小时；`ISOLATED_DRILL`可用于有限历史回执演练。计划文件本身不激活调度，不改写旧冻结计划。当前实现只覆盖所声明的窗口，调度运行范围与窗口到期后的处理仍须在激活配置中落实。

巡检逐期区分未来、待完成、未找到启动回执、仅有重复调用记录、有效结果尚缺、结束回执逾期、失败、准时和迟到。有效结果需满足已固定的启动器身份、父子回执关联、两个计划的观察摘要与时间、执行边界及禁单条件；同一cutoff的两份有效回执若指向不同观察，拒绝接纳。它核对的是已固定程序留下的执行证据，不会每分钟重跑行情或策略。

`current_status`说明当前扫描看到的状态；`deadline_status`保留首次超过准时期限时记录的结果。首次记为MISSING后，即使稍后收到带有较早信号时钟的有效回执，也只报告恢复，原缺口保持MISSING。已有准时观察后发生的重试失败，会报告当前失败，同时保留原准时观察证据。缺结束回执只表示证据缺失，不能由此断言进程不存在。

已读取源文件的字节摘要随后若变化或文件消失，巡检报告来源未确认，清空当前计数并明确标记旧行不是本次有效状态；不会把旧绿色数据继续当作新核验结果。时钟回退后保留最高已观察时点，直到实际时钟赶上前不恢复正常判断。

## 告警及中断

同一持续问题不在每次扫描重复生成告警；首次问题、明确升级、迟到和恢复形成批次事件。多个周期同时缺失会合为一条摘要，而不是连续弹出多条通知。没有启动器结束回执时，通知绑定巡检报告自身摘要，不伪造一个结束回执。

巡检先原子保存报告，再准备待发送事件；若两步之间中断，下一次从已发布的报告补齐事件。每次调用最多启动一个本机投递助手，待发事件按报告序号处理；内容必须与来源报告重新推导出的内容完全一致，重新计算摘要也不能替换消息。投递结果未知会持续计入`unconfirmed`，启用发送时使CLI返回非零，不会因下次没有新事件就悄悄变成全部已送达。

巡检本身使用独立的OS文件锁，不争用观察启动器的锁。源尝试数、输入字节数、单文件大小及报告/队列数有上限。报告和原始失败状态不覆盖；同一巡检目录固定同一计划和生产回执目录。这里仍是单份权威目录的本机一致性，不是对拥有本地文件修改权限者的密码学认证。

## 使用与剩余工作

```powershell
python -I -B tools/observation_watch.py plan --start '<future-UTC-hour>' --output '<new-plan.json>'
python -I -B tools/observation_watch.py check --plan '<new-plan.json>' --job-root '<launcher-receipts>' --watch-root '<separate-watch-directory>'
```

检查会保存本地巡检报告，但默认不发送通知。显式`--send`才尝试投递；计划和原回执输入不能用公开摘要替代。当前尚未将巡检注册为独立Windows任务，也未固定最终运行件与切换配置；维护者批准后的单一调度权切换、新72小时自然观察及通知用户看到确认继续待办。不要把手动CLI调用当作已经部署的独立监督。
