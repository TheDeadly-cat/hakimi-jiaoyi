# F6：历史窗口期限的独立复核

当前`binding()`在每次读取profile时校验`history_start`距离UTC当日不超过30天。用独立合成profile检查0天、30天、31天，前两者通过，31天报`bounded_simulation_history_window_required`。见[原始检查摘要](history-window-audit.json)。此检查没有读取旧数据库、连接SDK或发送订单，也没有模拟完整到期订单周期。

静态调用路径表明，`prepare`直接校验profile；`submit`、`recover`和`cancel`通过`store.profile`重新校验，再创建SDK连接。因此历史窗口过期会同时阻挡查询恢复与撤单入口，不只是阻止新提交。单独重新授权不会解除该限制，源码冻结检查也不会豁免它。`duplicate-probe`不创建SDK；它不是恢复或撤单的替代手段。

这属于当前短时验收工具的明确维护限制，不能按长期无人值守服务使用。本轮不通过修改旧数据库的history_start、源码摘要、订单身份或持久领取记录绕过限制。未来若要支持长期恢复，需要单独实现并验证可审计的查询窗口推进与已绑定订单定位机制，保留原始起点和完整历史，且继续拒绝重复提交；当前没有把该能力标为已实现。

当前T3尚未派发订单，仍由已有Unknown记录和正常交易时段条件阻挡。这个F6复核没有改变其执行权限，也不依赖当前账户原件来填补长期恢复证据。
